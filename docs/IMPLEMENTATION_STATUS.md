## 位置取得と背景地図の設定

ローカルサンプルの背景地図にはOpenStreetMapの標準タイルを設定しています。URLと帰属表示は `.env` で変更できます。タイルを事前取得する機能やオフライン保存は実装していません。本番の利用規模に応じたタイル提供元は別途選定します。[OpenStreetMapタイル利用方針](https://operations.osmfoundation.org/policies/tiles/)

Mapboxによる住所からの自動取得は、現在の開発環境では無効です。永続保存・表示用途に合う契約を確認し、`MAPBOX_TOKEN` と `GEOCODING_PERMANENT_ENABLED=true` を設定した場合にだけ動作します。キーや契約なしで外部検索を行いません。API実接続は未検証で、候補応答と競合処理は模擬応答で検証しています。[Mapbox Geocoding API](https://docs.mapbox.com/api/search/geocoding/)

## 続く実装

次の項目は設計に含まれていますが、今回の版では未実装または一部実装です。

- 日別勤務・休み・会議の専用編集画面、勤務希望の複数時間帯、利用者別の予定表。
- 定期訪問ルールと重複しない生成、自動調整の候補作成と適用。
- 顧客ごとの担当可能者、調整期限・日付未定の訪問、地点別の移動時間。現在は管理範囲の標準移動15分で検証。
- 地図の候補選択画面、ピンをドラッグして修正、営業所マーカー、クラスタ表示、位置取得の利用量上限と提供者障害の一括停止。
- 会社基本情報の編集・会社停止・オーナー交代、将来日を指定する所属変更。現在の所属変更は操作日を適用日として履歴化。
- 給与の概算と営業所別費用配賦。現在の集計は訪問時間であり、勤務時間や給与額には使用しない。
- 過去の全公開版を復元できる履歴。現在は最後の公開内容と操作概要の履歴を保存。
- デスクトップJSONの移行、印刷用画面、全営業所の大量データに対するページ分割・負荷試験。
- 本番の配備構成、バックアップ・復旧手順と試験、メール連携。LINE配信は元から拡張候補。

公開運用へ移る前に、本番環境の設定、上記の未実装部分の取捨選択、データ移行と復旧試験を実施します。ローカル開発環境は他のPCから接続できない `127.0.0.1` に限定しています。

## 設計からの現時点の差分

所在地は初回実装ではclients内に保持し、独立したlocationsテーブルと営業所所在地の座標は次段階です。勤務希望の明細は構造を検証したJSONBで保存しています。公開予定はスタッフごとの最新データを保持し、全公開版の履歴テーブルは追加予定です。これらを実装済みの設計項目として扱わず、既存データを保つ追加マイグレーションで段階的に拡張します。

認可は各ServiceとRepositoryで実行し、会社・管理範囲の複合外部キーとRLSで保護しています。ユーザーのroleと全所属関係を横断する遅延制約トリガー、API仕様からのフロントエンド型生成は追加予定です。

## 代理入力・オーナー本人の使い方

1. 代理入力は「勤務希望」で対象月・スタッフの「代理入力」を選び、日ごとの希望を入力して「下書きを保存」→「勤務希望を代理提出」。月がなければ先に「募集期間を設定」します。
2. 提出済みの内容は理由を入力して「差し戻して編集」。締切後も差し戻した希望は修正・再提出できます。未提出で締切を過ぎた月は募集期間を延長します。
3. 本人分は「自分の予定・希望」で既存の自分のスタッフ情報を選択するか、新規登録します。その後「自分の勤務希望」で入力・保存・提出できます。
4. 「自分の訪問予定」では本人の担当予定を確認・編集し、「自分の訪問予定を追加」で本人を初期選択して登録できます。全体の「訪問予定」でも本人を担当者に指定できます。

今回の追加では既存の `staff.user_id`、勤務希望、お知らせ、履歴を使用するため、DB構造の追加変更はありません。紐付けは本人が明示的に行い、既存データからの名前による自動推定は行いません。

## 検証方法

`backend/tests` は専用DB `atelier_test` を使用します。会社・オーナー分離、RLS、複合外部キー、本人だけの公開情報、CSRF、勤務希望、重複、楽観ロック、並行操作、所属・雇用履歴、アカウント失効、位置取得の競合を検証します。通常の開発DB `atelier` をテストで消去しません。

`frontend/tests` はローカルの架空サンプルを使い、オーナー・管理者・メンバーの画面、入力欄、地図、スマートフォンの勤務希望を実ブラウザーで確認します。メンバーのサンプル勤務希望にはテストで下書きを保存します。日・週のドラッグ更新はAPIテストでも検証します。

追加した `owner-requests.spec.ts` は専用DB `atelier_test` とテスト専用APIプロセスを使用し、本人スタッフの新規登録・既存紐付け、本人希望の提出、代理入力・提出・差し戻し、本人と対象スタッフのデータ分離、既存の希望と訪問の引継ぎを確認します。実際に使用している開発DBのオーナーとスタッフの紐付けは変更しません。このテストとpytestは同じ専用DBを初期化するため、同時実行はしません。

確認画像は `deliverables` に保存しています。PCは1440×1000、スマートフォンは390×844を検証しました。想定した全件数での性能検証や本番運用の認定を意味するものではありません。

2026年10月4日の確認結果は、PostgreSQLを使うAPIテスト28件成功、Microsoft Edgeによる画面操作テスト5件成功（既存3件・追加2件）、TypeScriptとViteのビルド成功です。画面テストには訪問カードを縦横にドラッグして元の位置に戻す操作も含みます。`alembic check` は追加の差分なし、コードの未使用参照等を調べるRuffのFルールも成功しました。テスト用HTTPクライアントに非推奨の警告がありますが、失敗はありません。
